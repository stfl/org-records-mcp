#+TITLE: Contributing to org-records-mcp

This page is for changing org-records-mcp: the environment, the checks a commit has to
pass, and the conventions the code keeps. Using org-records-mcp is the [[file:README.org][README]].

* The devshell

Every tool the checks need — Emacs 31, eask, just, shellcheck, shfmt, zizmor —
comes from the Nix devshell, and nothing is expected on your own =PATH=:

#+begin_src bash
nix develop            # a shell with the tools
nix develop --command just check    # or a single command in it
#+end_src

With direnv, =.envrc= enters the shell for you when you =cd= into the checkout.

Scripts in this repository never enter the devshell themselves: they are written
against a =PATH= that already has their tools, and the caller provides it.

* The checks

=just check= is the whole gate, and the pre-commit hook runs exactly it:

| Recipe       | Does                                                                        |
|--------------+-----------------------------------------------------------------------------|
| =just fmt=   | elisp-autofmt on =org-records-mcp.el=, =shfmt -i 4= on the shell scripts    |
| =just lint=  | byte-compile, elisp-lint, script byte-compile, org-lint, shellcheck, zizmor |
| =just test=  | the ERT suite, through =scripts/run-tests.sh=                               |
| =just check= | all three, in that order                                                    |

Both quiet stages keep their evidence: a failing lint stage writes
=.lint-output.txt=, and the test run always writes =.test-output.txt=, with the
ERT summary on success and the failure block on failure.

=just lint= org-lints =README.org=, this page and every =docs/*.org= page, each
from its own directory, so a link to a page that does not exist fails the
commit.

The suite checks its dependencies before it runs and stops with the remedy when
the installed =mcp-server-lib= is older than the version =Eask= requires.
Raising that requirement does not refresh a checkout that already has the
dependency: an installed MELPA snapshot carries a date version, which outranks
a release number, so =eask install-deps= leaves it in place and the suite then
fails in bulk, in places that each look like something else. A fresh worktree
and CI never see it, since both install from nothing.

CI runs the same suite on every branch you push and on every pull request, over
Emacs 31.1 and 30.2 on Linux and macOS. It is the wider net: the local gates run
the Emacs of the devshell only.

* Formatting

=just fmt= is the only formatter, and =scripts/format-elisp.el= refuses to run
under an Emacs other than 31 or one without elisp-autofmt, so the layout is the
same on every machine.

=org-records-mcp.el= is laid out at 70 columns, which it carries as a file-local
variable; other Elisp in the repository goes to the 100 columns
=.dir-locals.el= sets. =.dir-locals.el= also carries the =elisp-lint-indent-specs=
for the macros in this repository — a new =with-= macro belongs in that list, or
the linter reindents every use of it.

* Committing

The pre-commit hook runs =just check=, which needs the devshell, so commit from
inside it:

#+begin_src bash
nix develop --command git commit
#+end_src

Commit subjects follow the =type(scope): summary= form the history uses, written
in the imperative: =fix(clock): let the session clock decide which clock is
active=.

* Writing the code

org-records-mcp is a thin MCP adapter on top of Org-mode. Its value is a faithful, stable
mapping between MCP primitives and Org's existing semantics, so a change does not
reinvent what Org already does. Before adding or changing parsing, navigation,
clock, drawer, tag or TODO-state logic, look for the Org API first:

| Instead of                            | Use                                                                  |
|---------------------------------------+----------------------------------------------------------------------|
| manual level-regex walks              | =org-find-olp=, =org-get-outline-path=                               |
| a level regex over the tree           | =org-map-entries=, =org-map-tree=, =org-element-map=                 |
| hand-rolled drawer skipping           | =org-end-of-meta-data=                                               |
| chained =org-entry-get=               | =org-heading-components=, =org-element-at-point=                     |
| inserting heading asterisks by hand   | =org-insert-subheading=                                              |
| CLOCK regex scanners                  | =org-clock-in= / =-out=, =org-find-open-clocks=, =org-clock-resolve= |
| custom drawer deletion                | =org-remove-empty-drawer-at=                                         |
| custom time and duration parsers      | =org-time-string-to-time=, =org-duration-from-minutes=               |
| manual LOGBOOK formatting             | =org-add-log-setup= + =org-store-log-note=                           |
| destructuring =org-todo-keywords=     | =org-todo-keywords-1=, =org-done-keywords=                           |
| custom tag parsing or tag regexps     | =org-tag-alist-to-groups=, =org-tag-re=                              |
| regex-based block or drawer detection | =org-element-parse-buffer=                                           |

When an Org API is genuinely missing or unsuitable, say why in a comment next to
the workaround, so the next person can re-evaluate it when Org moves on. Code
that already duplicates Org is replaced rather than extended.

** What a response field may hold

=json-encode= writes an elisp =nil= as JSON =null=, and =null= is not a value
this server sends. Every response field is a boolean, a list, or optional, and
each has one spelling:

| The field is            | Write it as             | Empty is |
|-------------------------+-------------------------+----------|
| a boolean               | =t= or =:json-false=    | =false=  |
| a list                  | =vconcat= over the list | =[]=     |
| a value a node may lack | left out of the alist   | absent   |

A generalised boolean written bare reaches a client as =true= or =null=, which
no client tests for, and a list written bare reaches it as =null=, which throws
on anything that reads a length. The third row is the node builder's rule,
stated for its readers in [[file:docs/reading.org][Reading Org content]]: a field the node has no value
for is left out rather than sent as null, so an answer says what the node has.

There is one place =null= is a value rather than an accident, and it is a
value in a vocabulary rather than a field of its own: a property map. A drawer
line has three states, so the map spells three, and =null= is the one that
says there is no line (see [[file:docs/writing.org][Changing Org content]]). It reaches a client in the
=before= a write echoes back, which is that map returned as it arrived. A
field genuinely nullable — one whose meaning is /unknown/, as distinct from
false, empty or absent — would need a row of its own in the table above before
it could be written. The surface has none.

** What a parameter is published as

Every tool parameter is published with its JSON type, declared by name in
=org-records-mcp--param-types=. =before=, =after= and =properties= mean
something different on different tools, so a tool taking one declares it in
=org-records-mcp--tool-param-types= instead. A new parameter is declared even
when it is a plain string: registration fails
on one the tables do not name, so a parameter cannot reach a client as the
string =mcp-server-lib= publishes by default. The census in the test suite
lists every tool's parameters and their types a second time, by hand, and a
parameter it does not list fails the suite.

A parameter taking a name from a closed set publishes the set as an =enum=. A
set the user configures is read when =org-records-mcp-enable= registers the
tools, so its kind reads the setting inside =org-records-mcp--param-schema=
rather than in a constant. Why the types are what they are is
[[file:docs/adr/0034-a-parameter-is-published-with-its-json-type.md][ADR 0034]]; what a client sees is [[file:docs/installation.org::*The types the tool schema publishes][The types the tool schema publishes]].

* Tests

The suite lives in =org-records-mcp-test.el= and runs with =just test=.

Org content under test is written as =defconst= constants, one for the file
before the call and one for the file after it, rather than built inline. The
result is then verified with a single regular expression matching the complete
Org file, so a test that passes has pinned the whole file, not the one line it
was looking at.

A run in batch keeps Org's state out of your Emacs, whether it is =just test= or
a probe that loads the suite with =eask exec emacs --batch=: the element caches
and the ID index each live in a directory of the run's own under
=temporary-file-directory=, deleted when it exits. When Org saves the ID index,
through =org-id-locations-save=, to a file anywhere else, the save writes
nothing and the test fails. The suite's tests bind =org-id-locations-file= to
=nil= so that no index is saved at all, which the guard permits; a test that
needs an index on disk binds it to a =make-temp-file=.

** What a test has to quantify over

Most of what a change claims is universal: a docstring, a refusal message or an
ADR says /every/ position the text can occupy, /every/ input that reaches this
refusal, /every/ write that rewrites headings. A test that exhibits one case is
evidence for /some/ and none at all for an /every/ — the suite encodes the
witness, goes green, and the green gets read as confirming the sentence in the
docstring.

Asking what fixture would distinguish a right implementation from a subtly
wrong one does not repair that, and the reason is worth knowing: naming one
needs a candidate wrong implementation, and the candidates that come to mind
are neighbours of the implementation just written. Someone cutting a suffix
asks what a subtly wrong suffix-cutter would do and writes fixtures with the
junk at the end, because a suffix-cutter is a machine about ends. The fixture
set portrays the algorithm rather than the claim, and asking harder yields more
of the same fixtures.

Work from the sentence instead. Write each claim as "for every X, P", name the
X you tested and the X you did not, and for each untested region say why the
construction covers it. A construction argument about a different operation
than the one the code performs covers nothing: =org-collect-keywords= follows a
=#+SETUPFILE:=, so a setupfile's keywords count when Org /reads/ them, and code
that subtracts a file's own lines from that reading has changed the operation
the argument was about.

The same distinction governs a claim about the suite rather than about the
code. "Nothing covers this" is itself universal — /for every test, it does not
cover this/ — and reading one test does not establish it. The claim is safe
when it accompanies a defect that reproduces, because a misbehaviour and a
green suite together entail that nothing pins the behaviour; there is no absent
test to go looking for and no way to be wrong about it. It is unsafe when it
accompanies behaviour that is correct: the suite then looks the same whether
the test exists or not, so the claim rests entirely on having searched, and a
docstring, a test name or a diff hunk is not a search. A census invites the
mistake — a docstring that says every write tool but one, a table that runs ten
of thirteen, and the remaining three pinned in a test of their own because they
need a digest and do not fit the table. The behaviour is right, so nothing the
suite prints says otherwise.

Four shapes carry this hazard, and each is recognisable before any of the code
is written:

- *A validator that classifies* :: it partitions its inputs into accepted and
  refused rather than transforming them, so the boundary is a property of the
  input space and not of the code. State the accept/refuse predicate as a
  sentence that never mentions how you compute it, and generate inputs from the
  sentence.

- *A refusal that echoes a value derived from its input* :: a =%s= filled by
  something computed from the input, rather than by the input itself or by a
  configured value. The advertised value has to be accepted for every input
  that can reach the refusal, not for the one picked to demonstrate the
  message; where checks run in sequence, a refusal echoing a derived value can
  hand back something a later check rejects. Run the advertised value back
  through the gate that produced the refusal, or prove it cannot fail one —
  ordering your own check last protects your own message and nothing else.

- *A set operation on values that can repeat* :: =delete=, =remove=,
  =cl-remove=, =seq-difference= or =member= over a collection whose elements
  come from user text rather than a fixed vocabulary, where set and multiset
  semantics part ways: =delete= removes every equal element. Ask whether the
  collection can carry duplicates — drawn from a file it always can — and
  remove one occurrence per subtrahend, which is usually what is meant.

- *A guard with a direction* :: a check firing on a transition A→B where B→A is
  reachable through the same tool with the same parameters. The inverse
  usually carries the same hazard and no guard. Write in the ADR, rather than
  the code, what the inverse does and why it needs none; one sentence. If you
  cannot write it, the guard is directional for no reason you can state. This
  one pays at design time, before any code exists.

* What a change owes the documentation

A change to anything a client or an Emacs user can observe updates the page that
documents it, in the same commit. An MCP tool, a resource template and a
=defcustom= are the obvious ones; so are a public variable, what the =initialize=
handshake reports, and the text of a refusal a client is meant to act on. The
test is whether someone outside =org-records-mcp.el= can see the difference, not which
kind of thing changed:

| Change                                    | Page                           |
|-------------------------------------------+--------------------------------|
| a read tool, a resource, a discovery tool | [[file:docs/reading.org][Reading Org content]]            |
| a heading's history, or what it reads     | [[file:docs/history.org][A heading's history]]            |
| a write tool, or write behaviour          | [[file:docs/writing.org][Changing Org content]]           |
| a query or view tool, or its settings     | [[file:docs/queries.org][Searching and named views]]      |
| a clock tool or clock setting             | [[file:docs/clocking.org][Clock tracking]]                 |
| which files a call may reach              | [[file:docs/file-access.org][Which files a call reaches]]     |
| link forms taken or returned              | [[file:docs/links.org][Addressing headings with links]] |
| installing, or registering with a client  | [[file:docs/installation.org][Installing org-records-mcp]]     |
| what the =initialize= handshake reports   | [[file:docs/installation.org][Installing org-records-mcp]]     |
| how a client encodes an argument          | [[file:docs/installation.org][Installing org-records-mcp]]     |

The README changes only when what org-records-mcp /is/ changes, or what it costs to run:
the tool count, the quickstart, a new limit. Everything else belongs to a page
above, linked from the README's table.

Decisions that shape the interface are recorded in [[file:docs/adr][docs/adr/]], one numbered
Markdown file each: what org-records-mcp does, and what that was chosen over. A change
that settles such a question adds one.

Terminology is fixed in [[file:CONTEXT.md][CONTEXT.md]]: the words there are the words the docs and the
error messages use.
