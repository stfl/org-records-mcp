#+TITLE: Addressing headings with links

This page answers how a call names a heading, which links org-records-mcp takes,
and which link it gives back. The [[file:../README.org][README]] introduces the server itself.

* Addressing headings with links

Every tool that names a heading takes a native Org link, the text Org
resolves inside =[[…]]=, and nothing else, and resolves it the way Org does:
Org's own link parser, Org's ID index for =id:=, and =org-link-search= for
=::*Title= and =::#custom-id=. The heading a call reaches is the heading
=C-c C-o= opens in Emacs, so a link copied out of Emacs works unchanged, and a
link a client finds in a body is the next call's =link=:

| Link                               | Addresses                                  |
|------------------------------------+--------------------------------------------|
| =id:<id>=                          | the heading with that =ID= property        |
| =file:/abs/path.org::#<custom-id>= | the heading with that =CUSTOM_ID= property |
| =file:/abs/path.org::*<title>=     | the first heading with that title          |
| =file:/abs/path.org=               | the whole file                             |
| =id:<id>= (file-level drawer)      | the whole file                             |

- A link may be bare or bracketed, with or without a description:
  =id:abc=, =[[id:abc]]= and =[[id:abc][Project Alpha]]= name the same
  heading.
- org-records-mcp resolves a link with Org's own lookup. For an ID, that is Emacs's ID
  index, read with =org-id-find-id-file=, or =org-id-find-id-in-file= in each
  file a call names in =files= (see [[file:file-access.org::*Naming the file of an ID][Naming the file of an ID]]). The file
  the index names must be one the call may reach, an allowed file or one
  =org-records-mcp-file-scope-override= permits, before org-records-mcp reads
  it, so an index entry for a remote file, or for a file the call may not
  reach, is refused without touching that file. When the index lacks the ID,
  or names a file that does not hold it,
  org-records-mcp rescans the index once, as =org-id-find= does. For the part after
  =::=, it is =org-link-search=. The search part of an =id:= link, as in
  =id:<id>::*Review=, runs within that heading's subtree; a =file:= link
  searches the whole file. A title that matches several headings resolves to
  the first, as it does in Org, and =::<n>= in a =file:= link goes to line /n/.
  A search that matches nothing is an error; org-records-mcp never offers to create
  the heading.
- A heading is whatever Org's parser takes for one. A line that starts with
  stars and a space is a heading even inside a block such as
  =#+begin_example= or =#+begin_src=, and the block breaks there: reads list
  that line as a heading, and a title link reaches it. Inside a block, Org
  escapes such a line with a comma, as =,* Note=; that line is no heading, and
  reads return it with its comma. =org-node-create= and =org-node-set-content= refuse a
  body with an unescaped star line inside a block; send it escaped.
- A link is resolved, never followed: your windows, narrowing, point, folding
  and marks stay as they were, even when the buffer is narrowed to another
  subtree, and so do the buffers you have open. A tool works in the buffer
  visiting the heading's file; when no buffer visits it, the tool opens one and
  leaves it open.
- A =file:= link names its file, and an =id:= link the file Emacs's ID index
  places its ID in. Either reaches the allowed files and any Org file
  =org-records-mcp-file-scope-override= permits (see
  [[file:file-access.org::*Configuring the scope override][Configuring the scope override]]).
- An =id:= link whose =ID= sits in a file-level property drawer, before the
  first heading, where org-roam keeps the =ID= of a file node, addresses the
  whole file, as =org-id-open= opens the file at its top. In =org-node-read=,
  =org-node-text= and the =org://{link}= resource it reads exactly as the
  file's =file:= link without a search part does. With a search part, as in
  =id:<id>::*Review=, it searches the whole file.
- A link to a whole file — a =file:= link without a search part, or an =id:=
  link to a file-level property drawer — reaches four write tools.
  =org-file-set-setting= takes it as the file whose =#+= settings to write, and
  a link naming a /heading/ there writes the heading's file, since those
  settings are file-wide; =org-node-set-properties= takes it as the node to
  write, and writes that file's own drawer; =org-node-create= and
  =org-node-refile= take it as =parent=, the top level of that file. Every
  other write tool needs a heading and refuses it
  (see [[file:writing.org::*Which tools a file's link reaches][Which tools a file's link reaches]]).

Two link forms are taken: =id:=, and =file:= with a full local path, with or
without a =::*Title=, =::#custom-id= or =::<n>= search. A link is resolved,
never run or opened, and anything else is refused before any file is opened.

org-records-mcp also refuses:

- a value that is not text: a number, =true=, or a non-empty array or object. The
  refusal names the parameter and what arrived, in JSON's words, before any
  parsing:

  #+begin_example
  parent must be a string, not true
  #+end_example
- a string that is no link: a bare ID, a bare path, a path with an outline
  path such as =/home/user/org/projects.org#Parent/Child=, a title on its own,
  or a link behind =org://=. The error names the link forms to send instead,
  and nothing is looked up. Bracketed, as =[[/home/user/org/projects.org#Parent/Child]]=,
  such a path is a link to a file that does not exist, refused as outside the
  allowed files with the same hint.

A link that org-records-mcp takes but cannot resolve, =Cannot find ID '...'= among
them, is refused in the unmarked default class; see [[file:writing.org::*How a refusal is classed][How a refusal is classed]]
for what the classes are and why this one carries no marker.

** A link parameter left blank

A link parameter is blank when it carries =null=, =false=, =""=, =[]=, ={}= or
nothing but whitespace — the values a client fills a parameter it is not using
with (see
[[file:writing.org::*What a blank parameter means][What a blank parameter means]]). What that means depends on whether the
parameter is required, and it is the same on every tool that takes a link:

- *Required and blank* is a call that did not send it, and the refusal names
  it rather than the value:

  #+begin_example
  Missing required parameter: link
  #+end_example

  =link= on every read, write and clock tool but =org-config-todo= is required,
  and so is =parent= on =org-node-create= and =org-node-refile=. The parameter is read before its
  file is opened, so nothing is looked up and nothing is written.

- *Optional and blank* means the call names no link, which each parameter has
  its own sense of: =previous_sibling= on =org-node-create= and
  =org-node-refile= puts the node last among its parent's children,
  =clock_out= says the call has no running clock to close, and =link= on
  =org-config-todo= asks for the global configuration. None is refused.

* Stable links

A title link, =file:<path>::*<title>=, is a convenience. It resolves as it
does in Org, to the first heading of the file whose title matches, letter case
aside and with the TODO keyword, the priority, statistics cookies and the tags
left out. It is ambiguous when two headings share a title, since it always
reaches the first of them, and it breaks when the heading is renamed.

For a stable address, give the heading an identifier:

- An =ID=, such as a UUID, in a file Emacs's ID index covers, for example an
  agenda file. The link is =id:<id>=.
- A =CUSTOM_ID=, unique within its file, in any other file. The link is
  =file:<path>::#<custom-id>=.

org-records-mcp adds neither on its own. Set one with the =properties= parameter of
=org-node-create= when the heading is created, or with =org-node-set-properties=
afterwards. Once a heading has one, every link org-records-mcp returns for it is the
stable one (see [[*Links org-records-mcp returns]]).

An =id:= link resolves through Emacs's ID index, to the file the index names,
as far as the allowed files and =org-records-mcp-file-scope-override= reach (see
[[file:file-access.org::*Naming the file of an ID][Naming the file of an ID]]). org-records-mcp does not add a new =ID= to that
index, so the first lookup of it rescans the index; a call that names the
heading's file in =files= avoids the rescan, and reaches an ID in a file Emacs
has not indexed.

* Links org-records-mcp returns

Every =link= field org-records-mcp returns is a native Org link: a write returns the
link to the node it changed, and every node in a read result, a query result
or an outline carries its own (see [[file:reading.org::*The node][The node]]). For a heading it is the link
=org-store-link= makes when it may only use the identifiers the heading already
has, chosen in this order:

| Node                                   | Returned link               |
|----------------------------------------+-----------------------------|
| heading with an =ID=                   | =id:<id>=                   |
| heading with a =CUSTOM_ID= and no =ID= | =file:<path>::#<custom-id>= |
| heading with neither                   | =file:<path>::*<title>=     |
| file with an =ID= of its own           | =id:<id>=                   |
| file with none                         | =file:<path>=               |

A file's =ID= is the one in its own property drawer, above the first heading,
where org-roam puts the ID of a file node.

=<path>= is the file name as Org writes it, with =~= for your home directory. A
title link leaves out the TODO keyword, the priority, statistics cookies and the
tags. It reaches the first heading with that title and breaks on rename; see
[[*Stable links]] for a link that does neither.

org-records-mcp creates no identifiers. No tool adds an =ID= or a =CUSTOM_ID= to a
heading, and a read leaves the file byte-for-byte unchanged, whether or not a
buffer visits it. A client that wants a stable link sets the identifier itself.

Your link settings do not change the returned link. org-records-mcp calls
=org-store-link= non-interactively and, for that call only, binds
=org-id-link-to-org-use-id= to =use-existing=, keeps =id:= links free of an
inherited ID and a search part, keeps the heading's search on =file:= links, and
ignores the active region, file search functions and other packages' link store
functions. Advice on =org-store-link= still runs. When it makes a link of
another type or edits the buffer, the call fails with an error that says so; a
write then reports that its change was made.
